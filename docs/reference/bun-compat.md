# Bun compatibility

Mycelium can run a small, deliberately partial subset of the [Bun](https://bun.sh) runtime's
global API on top of GraalJS, the same way it already implements Node-compat globals
(`process`, `Buffer`, `URL`, timers, ...) and 50+ Node core-module shims — see
[Language support](./languages.md) for the Node side.

This is a **first pass**, scoped narrowly on purpose. Read the "Not supported" section below
before assuming any given Bun API works.

## Runtime detection

Unlike Node-compat globals (injected into every JS `Context` unconditionally), the `Bun`
global is only injected when Mycelium detects the script being run/imported actually looks
like Bun code. Detection checks, in priority order (Node signals always win — a directory
with both a Bun signal and a Node signal is treated as Node, the best-tested path):

1. **Node signals** (checked first, per the "Node is the trojan horse" strategy): a
   `package-lock.json`, `pnpm-lock.yaml`, or `yarn.lock` in the entry file's directory or any
   ancestor — if found, `Bun` is **not** injected, even if a Bun signal is also present.
2. **Bun signals**: a `bun.lockb` (Bun's binary lockfile — presence alone is checked, its
   contents are never parsed) or `bunfig.toml` in the entry file's directory or any ancestor.
3. **Source-level signal**: a `bun:`-prefixed import/require specifier anywhere in the
   source being evaluated (`import ... from "bun:sqlite"`, `require("bun:ffi")`,
   `import("bun:test")`, ...) — checked independently of the filesystem signals above, so a
   single file using a `bun:` import gets `Bun` injected even with no lockfile around it.

Node's own globals (`process`, `Buffer`, `URL`, ...) are **not** hidden when Bun is detected —
a detected-Bun script sees both, matching real Bun (which also implements most of Node's
global surface for compat).

Deno detection/globals are a separate, unimplemented follow-up — this page and its
implementation only ever decide "is this Bun", never "is this Deno".

## What's supported

### `Bun.file(path)`

Returns a `BunFile`-like object. Bypasses Mycelium's `InterceptingFileSystem` entirely and
reads directly via `java.nio.file.Files`/`Paths` — the same intentional bypass the
`node-stdlib/fs.mjs` shim uses, and (verified against real Bun) it means a **relative** path
resolves against the JVM process's actual working directory, not the importing script's own
directory — matching real Bun, which also resolves `Bun.file`'s relative paths against
`process.cwd()`, not the script's directory.

- `.text()` — `Promise<string>`. Rejects with an `ENOENT`-shaped error for a missing file
  (`.code === "ENOENT"`, message `"ENOENT: no such file or directory, open '<path>'"`) —
  verified against real Bun 1.3.13.
- `.exists()` — `Promise<boolean>`. `false` for a missing file, never rejects.
- `.arrayBuffer()` — `Promise<ArrayBuffer>`. Same ENOENT rejection as `.text()` for a missing
  file.
- `.json()` — `Promise<any>`, sugar over `.text()` + `JSON.parse`.
- `.size` — lazily stat'd; `0` for a missing file (not `NaN`/an exception).
- `.type` — a MIME-type guess based purely on the file extension (never stats the file, so a
  missing file still gets a guessed type). The lookup table (454 entries, covering
  text/image/audio/video/application/font categories plus a deliberately broad source-code
  extension list, since this is a polyglot runtime) is generated by
  `tooling/generate-bun-mime-table.mjs` by probing a real `bun` 1.3.13 process — see that
  script's header comment and `BUN_INIT_SCRIPT`'s own `MIME_TYPES` comment in `Mycelium.kt`
  for the exact generation strategy (exhaustive 1-2 letter extensions, exhaustive 3-letter
  extensions minus vendor-specific ones, plus a curated 4+ letter corpus). This is **not**
  exhaustive against Bun's full `mime-db` (which runs into the thousands of entries across
  all lengths): anything outside the table falls back to `application/octet-stream` rather
  than a further guess, same as real Bun's own fallback for extensions its `mime-db` doesn't
  register either — the two known, accepted gaps are (1) ~338 3-letter extensions real Bun
  maps to a vendor-specific (`vnd.`-tagged) MIME type, deliberately excluded as not
  plausible for a real user to hit, and (2) any 4+ letter extension real Bun's `mime-db`
  knows about that isn't in the curated corpus.
- `.stream()` is **not implemented**.

### `Bun.serve({ fetch, port, hostname, development, error })`

Backed by the same `com.sun.net.httpserver.HttpServer` primitive as the `node-stdlib/http.mjs`
shim's `Server` class (single JDK server, one request at a time — see that file's own
single-threaded-Context caveat, which this inherits identically).

- `fetch(req, server)` receives a minimal Fetch-API-shaped `Request` (`.method`, `.url`
  as an absolute URL string, `.headers` — a `Headers`-like object with `.get`/`.set`/`.has`,
  `.text()`/`.json()`/`.arrayBuffer()`/`.clone()`).
- Returning a `Response` (constructor: `new Response(body, { status, statusText, headers })`,
  with `.status`/`.headers`/`.text()`/`.json()`/`.ok`) sends it back verbatim.
- Returning something that isn't a `Response` is treated as **success**, not an error —
  verified against real Bun 1.3.13: status 200, body exactly `"Welcome to Bun! To get
  started, return a Response object."`
- A thrown/rejected `fetch` is logged to stderr and answered with a fixed 500 response —
  verified against real Bun 1.3.13 with `development: false`: body exactly `"Something went
  wrong!"`, `Content-Type: text/plain`. This shim **always** behaves like
  `development: false`; real Bun's actual dev-mode default is a large inline HTML error
  overlay, which is deliberately not replicated.
- An `error(err)` option, if provided, is tried first (sync or async); falling through to
  the fixed 500 above if it itself throws/rejects or returns nothing.
- Default port (when `port` is omitted) is `3000`, matching Bun's documented default.
  `Request`/`Response`/`Headers` are injected as bare globals too (only within a
  Bun-detected script — they are not leaked into plain Node-compat scripts).
- Returned server handle: `.port`, `.hostname`, `.development`, `.url`, `.fetch`, `.stop()`,
  `.reload({ fetch })`.
- **Not implemented (this HTTP-only path)**: TLS options, unix socket listening,
  `idleTimeout`, request/response streaming bodies (bodies are read/written fully-buffered,
  never as a `ReadableStream`).
- **Known limitation: non-ASCII header values are mangled.** Real Bun preserves raw
  non-ASCII bytes in request/response header values byte-for-byte — verified directly: a
  request header value containing literal UTF-8 bytes for `é` sent to a real `bun`
  1.3.13 `Bun.serve` process comes back exactly as `é` when echoed into a response header.
  This shim's `Bun.serve`, backed by `com.sun.net.httpserver.HttpServer`, does **not**
  preserve this — the same non-ASCII byte round-trip comes back as `?` (the JDK's header
  parsing/writing appears to coerce header values to ASCII internally). This was found via
  fuzz testing (`BunFuzzTest.kt`) and is a real, confirmed divergence from real Bun, not a
  spec ambiguity — RFC 7230 header field-values are formally ASCII-only (the legacy
  "obs-text" byte range has no defined character semantics), so real Bun's UTF-8-preserving
  behavior is itself an extension beyond the spec, one this shim doesn't replicate. Fixing
  this would likely require replacing the JDK `HttpServer` backing (or post-processing raw
  header bytes before the JDK's own parsing touches them), which hasn't been attempted here
  — documented as a known gap rather than silently fixed or hidden.

### WebSocket support in `Bun.serve({ websocket })`

`Bun.serve({ fetch, websocket })` — real Bun's `server.upgrade(req, { data, headers })` +
`websocket: { open, message, close, ping, pong, drain, sendPings }` shape.

**Architecturally, this is a wholesale separate server implementation from the plain-HTTP
`Bun.serve` above, not an extension of it.** `com.sun.net.httpserver.HttpServer` (the plain
path's backing) cannot support a WebSocket upgrade at all: `HttpExchange` has no API to hijack
the underlying socket, and calling `sendResponseHeaders` with no fixed `Content-Length`
installs a chunked- or fixed-length framing filter on the response stream that's incompatible
with then writing a raw byte stream (the WebSocket frames) over the same connection — there is
no clean way to keep using `HttpServer` once a connection needs to stop looking like discrete
request/response pairs. So: **when, and only when, `options.websocket` is present**, `Bun.serve`
routes to a completely separate code path that runs its own minimal HTTP/1.1 server directly
over `java.net.ServerSocket`/`Socket` — parsing requests, performing the RFC 6455 upgrade
handshake, and framing WebSocket messages entirely by hand. **The plain-HTTP `Bun.serve` path
(no `websocket` option) is completely unchanged** — same `HttpServer` backing, same code,
verified by BunCompatTest.kt's/BunFuzzTest.kt's full existing suite still passing unmodified.

What's implemented on the WebSocket-capable path:

- RFC 6455 opening handshake: validates `Upgrade: websocket` / `Connection: Upgrade` /
  `Sec-WebSocket-Key`, computes `Sec-WebSocket-Accept` via the RFC's fixed formula
  (`base64(SHA-1(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`) — independently
  cross-checked in `BunSocketTest.kt` (a from-scratch client implementation computes its own
  expected Accept header and asserts the server's matches, rather than trusting the shim's own
  math).
- `server.upgrade(req, { data, headers })` — returns `true`/`false` exactly like real Bun
  (`false` for a non-upgrade request or a request already upgraded, never throws); `data`
  becomes `ws.data`, `headers` are merged into the 101 response.
- `ServerWebSocket`: `.send()`/`.sendText()`/`.sendBinary()`, `.ping()`/`.pong()` (auto-replies
  to an incoming Ping with a Pong unless `sendPings: false`), `.close(code, reason)` (sends a
  Close frame then closes the socket — does **not** wait for the peer's own Close-frame
  acknowledgement first, a simplification vs. the strict RFC closing handshake),
  `.terminate()` (abrupt, `SO_LINGER(0)`), `.subscribe()`/`.unsubscribe()`/`.isSubscribed()`/
  `.subscriptions`, `.data`, `.readyState`, `.remoteAddress`, `.cork()` (runs the callback
  synchronously — no actual batching optimization, since every write here is already a
  synchronous blocking Java I/O call).
- `server.publish(topic, data)` / `ws.publish()`/`.publishText()`/`.publishBinary()` — pub/sub
  across every WebSocket connection this one `Bun.serve()` call owns.
- Message fragmentation (continuation frames) is reassembled correctly; both directions were
  exercised with real fragmented input in `BunSocketTest.kt`
  (`bunServeWebSocketFragmentedFrames`).
- Messages spanning the 16-bit and 64-bit RFC 6455 extended-length encoding are handled (a
  200 KiB round-trip is exercised live in `bunServeWebSocketLargeMessage`).

**Known gaps on this path, not silently faked:**

- **No HTTP keep-alive** — every connection is closed after exactly one HTTP request/response
  (or, if upgraded, runs its WebSocket lifetime and then closes) — a real client that expects
  to reuse a connection for a second plain HTTP request will find it already closed.
- **No chunked request bodies** — `Content-Length` only.
- **No permessage-deflate (WebSocket compression)** — the `compress` argument accepted by
  `.send()`/`.publish()`/etc. for API-shape compatibility is silently ignored (never actually
  compresses); a client that requires compression will simply get an uncompressed frame.
- **`idleTimeout`/`maxPayloadLength`/`backpressureLimit`/`closeOnBackpressureLimit` are not
  enforced.**
- **No TLS, no unix-socket listening** for this path either.
- **The closing handshake doesn't wait for the peer's Close-frame acknowledgement** before
  tearing down the TCP connection (see `.close()` above).

### `Bun.connect(options)` / `Bun.listen(options)` — raw TCP sockets

`Bun.connect({ hostname, port, socket, data })` (client) and
`Bun.listen({ hostname, port, socket, data })` (server), both backed by plain
`java.net.Socket`/`java.net.ServerSocket`. `SocketHandler` callbacks implemented:
`open`/`data`/`close`/`error`/`end`/`connectError`/`timeout` (`drain`/`handshake` are accepted
as handler properties for API-shape compatibility but never invoked — see below).
`Socket<Data>` instance surface: `.write()`/`.end()`/`.ref()`/`.unref()`/`.timeout()`/
`.terminate()`/`.shutdown()`/`.flush()`/`.reload()`/`.readyState`/`.remoteAddress`/
`.remotePort`/`.remoteFamily`/`.localAddress`/`.localPort`. `Bun.listen`'s returned
`TCPSocketListener`: `.port`/`.hostname`/`.data`/`.stop()`/`.ref()`/`.unref()`/`.reload()`.

- **Not implemented**: TLS (`{ tls: ... }`), unix domain sockets (`{ unix: ... }`), fd-based
  sockets (`{ fd: ... }`) — all throw a clear, specific error rather than silently behaving
  like a plain TCP socket. `socket.upgradeTLS()` doesn't exist. Backpressure is never actually
  reported (every write is a synchronous blocking Java I/O call, so `.write()` either fully
  succeeds or returns `-1`, never a partial/backpressure signal) — the `drain` handler is
  therefore never invoked.
- Verified against real Bun 1.3.13's documented `bun.d.ts` type shapes (this repo has a full
  `bun` source checkout available for cross-referencing exact signatures, e.g. `readyState`'s
  numeric meanings) — **not independently re-verified by hand-probing every field against a
  live process**, unlike the MIME table/`Bun.write`/`Bun.spawn` sections above. Live
  wire-protocol correctness (the part that actually matters for interop) IS checked in both
  directions in `BunSocketTest.kt`: the shim as a `Bun.connect` client against a real `bun`
  `Bun.listen` server, and a real `bun` `Bun.connect` client against the shim's own
  `Bun.listen` server — see that file's own top comment.

### `Bun.udpSocket(options)`

`Bun.udpSocket({ hostname, port, socket })` (unconnected — `socket.data(sock, buf, port,
address)`, `sock.send(data, port, address)`) and `Bun.udpSocket({ connect: { hostname, port },
socket })` (connected to a fixed peer — `sock.send(data)` takes no destination), backed by
`java.net.DatagramSocket`. `sendMany` matches real Bun's documented shapes: a flat
`[data, data, ...]` array for a connected socket, a flat
`[data, port, address, data, port, address, ...]` triplet array for an unconnected one.

- Not exercised against a real `bun` UDP peer in `BunSocketTest.kt` (only shim-to-shim) —
  unlike the TCP/WebSocket sections above, there is no live-parity check for this one yet.
- No TLS-equivalent (DTLS) — not a thing real Bun's UDP socket supports either.

### Concurrency model for all of the above (and why it's structured this way)

None of `Bun.connect`/`Bun.listen`/`Bun.udpSocket`/the WebSocket path spawn a dedicated
`java.lang.Thread` to block on socket I/O and call back into the shared GraalJS `Context` —
that pattern (used by `node-stdlib/net.mjs`'s own `Socket#_startReader`/`Server#listen`) is
NOT safe in general: `TimerManager.kt`'s own doc comment and `node-stdlib/child_process.mjs`'s
`_startIoThread` doc comment both describe an actually-hit bug in this codebase's history — a
background `Thread` newly started from a guest callback isn't guaranteed a clean shot at
(re-)entering the shared, non-multithreaded-by-default GraalJS Context, and losing that race
throws `IllegalStateException: Multi threaded access requested ... but is not allowed` *before
a single line of the thread's own body runs*. Instead, every accept/read/receive loop here is
driven by `globalThis.setTimeout` ticks on whichever thread already owns the Context (the same
thread that called `runFile`/`eval`) — each socket gets a short `SO_TIMEOUT` (~20ms); each tick
attempts one bounded-blocking read/accept/receive, delivering data (or a new connection)
immediately and rescheduling with zero delay to drain a burst promptly, while a
`SocketTimeoutException` (nothing arrived within the bound) just reschedules the next poll.
HTTP request parsing and WebSocket framing on the `Bun.serve({ websocket })` path additionally
buffer raw bytes across ticks and parse incrementally, so a request/frame arriving fragmented
across several small reads (or several arriving in one read) is handled correctly without ever
blocking on a read for more than one poll's timeout. This means a listening
`Bun.listen`/`Bun.serve({ websocket })` server (or an open `Bun.connect` socket) keeps
`runFile`'s event loop alive for as long as it's open, matching real Node/Bun/Deno's own
"the process stays alive while a listener is open" behavior — a script must explicitly
`.stop()`/`.close()`/`.terminate()` everything it opened, or `runFile` never returns.

### `Bun.env`

The exact same object as `process.env` (`Bun.env === process.env` is `true`, verified against
real Bun 1.3.13) — reads/writes go through the same env-override-tracking proxy
`PROCESS_INIT_SCRIPT` already sets up, not a separate implementation.

### `Bun.argv`

Shape matches Node's `process.argv` convention: `[execPath, scriptPath, ...args]` — verified
against real Bun 1.3.13 (`bun run script.js foo bar` reports
`[<bun binary path>, <script path>, "foo", "bar"]`). Mycelium's shim can only reconstruct the
first two elements: `argv[0]` comes from `ProcessHandle.current().info().command()` (the
running JVM launcher's own path — not a real `bun` binary path, since there isn't one),
`argv[1]` is the entry script's path when run via `Mycelium.runFile` (absent when the Bun
global was instead triggered via `Mycelium.evalModule`, which has no file path to report).
**No trailing CLI arguments are available at all** — Mycelium doesn't thread real process
argv through to guest code today (this is also why plain `process.argv` is unconditionally
`[]`; `Bun.argv` inherits the same limitation rather than fabricating values).

### `Bun.version` / `Bun.revision`

Non-empty, semver-shaped strings (`"1.3.13"` / an opaque revision marker) — explicitly
**not** a claim that Mycelium replicates that Bun release's behavior; the task's own scope
only required "plausible", not "matching your installed Bun".

### `Bun.write(destination, data)`

Bypasses `InterceptingFileSystem` the same way `Bun.file` does (relative `destination`
paths resolve against the JVM process's real cwd, not the running script's own directory —
see `Bun.file`'s note above for the same caveat). Returns `Promise<number>` (bytes
written), backed by `java.nio.file.Files.write`.

- `data` may be a string, an `ArrayBuffer`/`TypedArray`, or anything with an
  `.arrayBuffer()` method — this covers a `Bun.file()`-returned `BunFile` and a `Response`
  (verified against real Bun 1.3.13 that both are valid `Bun.write` sources).
- **Auto-creates missing parent directories** — verified against real Bun 1.3.13:
  `Bun.write('nosuchdir/out.txt', 'x')` succeeds and creates `nosuchdir/`, unlike Node's
  `fs.writeFile`/`fs.promises.writeFile`, which requires the directory to already exist and
  rejects `ENOENT` otherwise. This shim replicates that exact auto-create behavior via
  `Files.createDirectories` on the destination's parent before writing.
- Does **not** support a `Response`/`BunFile` as the *destination* (only as the `data`
  source) — real Bun's `Bun.write` accepts a `BunFile` destination too (writing to that
  file's path); this shim only accepts a plain path string as `destination`.

### `Bun.spawn(cmd, options)` / `Bun.spawnSync(cmd, options)`

Backed by `java.lang.ProcessBuilder`, the same primitive `node-stdlib/child_process.mjs`
uses (see that file's own doc comment, which this inherits identically: `spawnSync` reads
stdout to completion before stderr, so a command that fills the stderr pipe buffer while
blocked writing to a full stdout pipe could still hang; the async `spawn()` path polls via
`globalThis.setTimeout` ticks rather than a dedicated `Thread`, for the same
GraalJS-Context-reentrancy reason).

- `cmd` must be an array (`["cmd", "arg1", ...]`) — verified against real Bun 1.3.13 that a
  bare string `cmd` is rejected (`"cmd must be an array"`) and an empty array is rejected
  (`"cmd must not be empty"`); this shim throws the same `TypeError`s.
- `options.cwd` / `options.env` are supported (env replaces the child's environment
  wholesale when provided, matching `child_process.mjs`'s `applyEnv`).
- `options.stdin` / `options.stdout` / `options.stderr` only support the string modes
  `'pipe'` / `'ignore'` / `'inherit'` — **not** a numeric fd, not a `Bun.file()`/`Blob`
  write-target redirection (real Bun supports piping a subprocess's stdout straight to a
  file), and not `options.timeout`. An unsupported value throws a clear `TypeError` rather
  than silently misbehaving.
- Default modes match real Bun 1.3.13 (verified live): `spawn()` defaults to
  `stdin: 'ignore'`, `stdout: 'pipe'`, `stderr: 'inherit'`; `spawnSync()` defaults to
  `stdin: 'ignore'`, `stdout: 'pipe'`, `stderr: 'pipe'`.
- **`Bun.spawn(...)` throws synchronously** (not a rejected `.exited`) when the executable
  can't be found — verified against real Bun 1.3.13: `code: 'ENOENT'`, `errno: -2`, `path`
  set to the attempted executable, message exactly
  `Executable not found in $PATH: "<cmd>"`. `Bun.spawnSync` throws the same shape
  synchronously too.
- `Subprocess#stdout`/`#stderr` (when `'pipe'`) are a **deliberately simplified push-based
  stream-like object** — not a true WHATWG `ReadableStream` instance
  (`instanceof ReadableStream` is `false` here even though Mycelium separately implements a
  real one for `node:stream/web`, since this object is a different, simpler class).
  Supports `.getReader().read()` (standard `{ value, done }` shape), async-iteration, and
  non-standard convenience helpers `.text()`/`.arrayBuffer()`/`.json()` (real Bun requires
  wrapping in `new Response(stream)` or `Bun.readableStreamToText(stream)` for the
  equivalent — these are provided directly as a pragmatic shortcut, not a claim of matching
  real Bun's surface).
- `Subprocess#stdin` (when `'pipe'`) is a minimal `{ write(data), end(), flush() }` object,
  not a real `FileSink`.
- `Subprocess#exited` is a `Promise<number>` resolving to the process's raw exit status
  (matching real Bun: a `SIGTERM`-killed child's `.exited` resolves to `143`, i.e.
  `128 + 15`). `Subprocess#exitCode`/`#signalCode` follow Node's `child_process`
  convention instead (`exitCode: null, signalCode: 'SIGTERM'` for a signal-terminated
  child) — verified this exact asymmetry against real Bun 1.3.13.
- **Signal detection is a heuristic**: a raw exit status in `129..192` is decoded as
  `128 + signum` and reported as `exitCode: null, signalCode: 'SIG...'`, because Java's
  `Process` API exposes no other way to learn "this was a signal" (it doesn't expose the
  raw POSIX wait status the way libuv does). This correctly reproduces real Bun's behavior
  for the common case (verified: a child that self-terminates via `SIGTERM` reports
  `exitCode: null, signalCode: 'SIGTERM'` from `spawnSync`, matching real Bun 1.3.13) but is
  not a guaranteed-correct decode in every case (e.g. a process that legitimately calls
  `exit(143)` itself, without any signal involved, would be misreported as
  signal-terminated) — a real wait-status decode would need JNI or similar, out of scope
  here.
- `spawnSync`'s `resourceUsage` is always `{}` — real Bun populates OS resource-usage
  stats here; this shim doesn't (Java's `Process` API has no portable equivalent).
- `options.timeout`/`killSignal` (present on `node-stdlib/child_process.mjs`'s `spawn`) are
  **not** implemented for `Bun.spawn`/`Bun.spawnSync`.

## Not supported

Everything below is genuinely absent — not stubbed, not throwing a clear "not implemented"
error in every case, just not there. This list was checked against Bun's own published API
reference (not assumed from memory) and is **not exhaustive** — Bun's real `Bun` object has
well over 100 top-level members; only the ones most likely to be reached for are called out
by name:

- **`Bun.dlopen` / `bun:ffi`** — would need a JVM-side foreign-function mechanism (Java's
  Foreign Function & Memory API, or JNI). This is unrelated to Node's N-API (the ABI Node
  uses to load compiled `.node` addons) — conflating the two would be a factual error. Out of
  scope here because implementing FFI on the JVM is a separate, nontrivial effort, full stop.
- **`Bun.sqlite` / `bun:sqlite`** — would need a JVM SQLite binding (e.g. `sqlite-jdbc`) as a
  new dependency, plus a binding-shape decision. Not Bun-specific: Node's own `node:sqlite`
  has the identical open question in `TODO.md`.
- **`Bun.$`** (shell), **`Bun.hash`**, **`Bun.password`**, **`Bun.build`**,
  **`Bun.Transpiler`**, **`Bun.Glob`**,
  **`Bun.S3Client`/`Bun.s3`**, **`Bun.redis`**, **`Bun.SQL`/`Bun.sql`**, **`Bun.CryptoHasher`**,
  **`Bun.color`**, **`Bun.semver`**, **`Bun.Cookie`/`Bun.CookieMap`**, **`Bun.Worker`**,
  **`Bun.FileSystemRouter`**, **`Bun.plugin`**, **`Bun.peek`**,
  **`Bun.deepEquals`/`Bun.deepMatch`** — none implemented.
- **`Bun.connect`/`Bun.listen`/`Bun.udpSocket`, and WebSocket support in `Bun.serve` are now
  IMPLEMENTED** — see their own sections above (moved out of this list; TLS/unix-socket
  variants of all three, and a handful of other specifics, remain unimplemented as noted
  there).
- **Client-side `new WebSocket(url)`** (connecting OUT to a server, as opposed to
  `Bun.serve`'s server-side `ServerWebSocket`) is **not implemented** — this shim only
  implements the server side of the WebSocket protocol. A script that needs to connect to a
  remote WebSocket server (rather than accept incoming ones) needs real Bun/Node.
- **`bun:test`** — Bun's built-in test runner is not available; Mycelium has no Bun-specific
  test-runner integration.
- `Bun.serve`'s streaming request/response bodies (both the plain-HTTP and
  `websocket`-enabled paths).
- Deno compatibility (`Deno.*`) — a separate, unimplemented follow-up; not attempted here at
  all, including no detection logic for it.

If a script needs any of the above today, it needs to run under real Bun/Node, not Mycelium.
