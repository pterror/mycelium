# Truffle Mod Loader Feasibility: Bytecode Patches vs. AST Specialization

## Core Question

If a mod loader patches a Truffle language node class (e.g., GraalJS's `JSAddNode` or its
generated `JSAddNodeGen`) at class-load time via ASM/Mixin/`ClassFileTransformer`, does the
patch survive when Truffle's specialization machinery kicks in?

## Answer: Yes

Bytecode patches applied at class-load time survive Truffle specialization. The reason is
structural: modern Truffle DSL does not replace node *classes* during specialization. It
mutates a bitfield *within a single class instance*.

### Evidence

**1. `JSAddNodeGen` is the only generated class for `JSAddNode`.**

Extracted from `js-language-25.0.0.jar`
(`org.graalvm.js:js-language:25.0.0`, Gradle cache):

- `JSAddNode` (abstract, hand-written) declares `@Specialization` methods:
  `doInt`, `doDouble`, `doBigInt`, `doString`, `doPrimitiveConversion`, etc.
- `JSAddNodeGen` (final, generated by Truffle DSL annotation processor) is a
  **single subclass** containing all specialization logic. No per-type-combination subclasses
  exist. The class hierarchy is:
  ```
  Node -> JavaScriptBaseNode -> JavaScriptNode -> JSBinaryNode -> JSAddNode -> JSAddNodeGen
  ```

**2. Specialization is a bitfield mutation, not a class swap.**

`JSAddNodeGen` has a field `private int state_0_` (one bit per specialization branch).
Disassembly of `executeAndSpecialize(Object, Object)` shows the actual specialization path:

```
getfield  state_0_:I
bipush    N          // bit for the new specialization
ior
putfield  state_0_:I
invokestatic JSAddNode.doInt / doDouble / ...
```

It reads `state_0_`, ORs in a bit, writes it back, then calls the matching static helper --
all on `this`. No new node allocation, no `Node.replace()` call.

**3. `Node.replace()` is almost never called in `js-language-25.0.0.jar`.**

Disassembled all 5,122 class files in the jar and searched for invocations of
`com.oracle.truffle.api.nodes.Node.replace(...)` and `NodeUtil.replaceChild(...)`.

Result: **1 call site** in the entire jar (`NodeFactory`, an AST-construction utility),
unrelated to hot-path type specialization. Zero `*Gen` classes call `replace()`.

**4. `Node.replace()` itself creates instances of statically-named classes.**

Examined `Node.replace(T, CharSequence)` in `truffle-api-25.0.0.jar`: it is `public final`,
delegates to `NodeUtil.replaceChild(parent, oldChild, newChild)`, which swaps a field
reference in the parent. The *new* node is always allocated by caller-side factory code
(e.g., `JSAddNode.create(...)` returning `new JSAddNodeGen(...)`). Since `new` resolves
through the classloader, a load-time patch to `JSAddNodeGen.class` is visible in any
replacement instance too.

## Graal JIT / Partial Evaluation

Graal's partial evaluator builds compiler IR by parsing the **actual loaded bytecode** of the
methods it inlines. There is no alternate data path that bypasses the classfile. Since Truffle
DSL does not generate additional hidden classes for specialization, whatever bytecode is
present in the `*Gen` class at class-definition time is exactly what PE compiles -- on both
the interpreter and compiled paths.

`state_0_` is `@CompilationFinal`, so PE treats it as a constant after the first compilation.
This means the JIT-compiled code folds away unactivated specialization branches entirely --
including any patched code in those branches, which is correct behavior (the patch is compiled
in when the branch activates).

## Caveats

### Generated class internals are not a public API

Patches must target the specific generated bytecode shape of the exact GraalJS/Truffle
version. Field names (`state_0_`, `concatStringsNode`), method names
(`executeAndSpecialize`, `execute_int_int0`), and the bit-layout of the state field all
change when upstream adds/removes/reorders `@Specialization` methods. This means:

- Mod loader patches are version-pinned to the Truffle language version.
- Automated patch generation (e.g., from a higher-level Mixin-style DSL) is strongly
  preferred over hand-written bytecode patches.

### Lock / CAS discipline

State-field mutation is guarded by `Node`'s lock and (since GR-31342) uses CAS-style
lock-free specialization via `InlineSupport.StateField`. A patch that adds new state bits
without participating in this discipline could introduce race conditions. Patches that
*wrap/observe* existing specializations (e.g., adding logging or redirect logic around
`execute()`) are safe; patches that add *new* specialization branches need to integrate with
the state-field machinery.

### Rare `replace()`-based rewrites

A small number of node families (inline caches, call-site dispatch, potentially
`PropertyCacheNode` chains) may still use `Node.replace()` for AST-level topology changes
(not type specialization). For these, the target class of the replacement is statically named
in factory code -- so patching that target class is sufficient. But each node family should be
verified individually per Truffle/GraalJS version.

### `@CompilationFinal` and deoptimization

If a patch changes the behavior of a method that Graal has already compiled (e.g., an
`execute()` override), the change takes effect only after deoptimization. Load-time patching
(before any code runs) avoids this entirely. Runtime patching (if ever attempted) would need
to trigger invalidation via `CompilerDirectives.transferToInterpreterAndInvalidate()`.

## Implications for Mod Loader Design

1. **Load-time `ClassFileTransformer` is the correct integration point.** A Java agent or
   custom classloader that intercepts `*Gen` classes before `defineClass()` is called gives
   full coverage of both interpreter and JIT-compiled paths.

2. **Patch the `*Gen` class, not only the abstract parent.** The abstract `JSAddNode` declares
   the specialization methods, but `JSAddNodeGen` contains the dispatch logic (`execute()`,
   `executeAndSpecialize()`) and the state field. Both may need patching depending on the
   mod's intent.

3. **Version-pin aggressively.** The generated class shape is a function of the Truffle DSL
   version *and* the upstream node's `@Specialization` declarations. Mycelium is already
   pinned at GraalVM 25.0.0; mod compatibility should be declared per GraalVM version.

4. **Prefer wrapping over injection.** Wrapping `execute()` (e.g., adding pre/post hooks via
   ASM method-enter/exit advice) is safer and more portable across versions than injecting
   into the state-machine internals of `executeAndSpecialize()`.
